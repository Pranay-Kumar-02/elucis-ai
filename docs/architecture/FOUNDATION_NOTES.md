# Foundation implementation notes

What the development foundation implements, where it follows the design exactly, and every place where implementation needed a decision the design did not make. Nothing here changes the SRS. Items marked **proposed** need the team's or the mentor's agreement before they are recorded in D11.

| IMP-33 | **Classification, themes and naming, simplified for milestone 2.** (1) **Cold start** (D03 SVC-09): no labelled training split exists, so Stage A (calibrated classifier) and confidence calibration are not used. Every label comes from CP-02 (`method='llm'`, `confidence` NULL, `calibrated` false) and nothing is routed to the review queue (deviation from A-12 until labels exist; the step 8 evaluation measures the labels instead). Sarcasm is deferred, so CP-02 has no sarcasm field. (2) **Model calls** go through `modules/analysis/tasks.run_task`: schema as Ollama `format`, Pydantic validation, the call's own rules (every key once; cited IDs among those supplied; no digits in a theme name), two retries with the error fed back (A-15), two retries with a short wait when the runtime is unreachable (then the step fails and the job retries), and a `llm_call_records` row per attempt with the `prompt_versions` ID. Prompts live in `elucis/ai/prompts.py` with a version and content hash; changing a prompt without a new version stops the run. Customer text is delimited as `<customer_feedback id=…>` with tags escaped (doc 10 §4); the live CP-02 test includes an injection attempt. (3) **Themes**: every run creates new themes (no identity matching across runs, no overrides, no small-theme second pass); themes of earlier runs are archived on activation.
